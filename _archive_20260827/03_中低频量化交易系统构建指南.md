# 中低频量化交易系统构建指南（个人开发者版）

> 成文日期：2026-08-27 ｜ 素材集群：finai-quant-research-20260827 ｜ 读者：有 Python 基础、预算有限、目标 A 股中低频（日线~小时级）的个人开发者
> 纪律声明：本文不构成任何投资建议，不承诺任何收益；技术方案贴合个人开发者实际，不涉及微秒级组件或商业级机房。

---

## 0. 执行摘要

一句话路线：**先数据、后回测、再模拟、最后小额实盘；运营件（日志、风控、对账、监控）从第一天就进版本库。**

展开说：把系统想成"四套环境 × 六层接口 + 四个运营支撑件"——research（研究）→ backtest（回测）→ paper（模拟盘）→ live（实盘）四套环境，DataSource / FeaturePipeline / SignalGenerator / PortfolioConstructor / OrderRouter / RiskManager 六层核心接口，外加监控、审计日志、报表闭环、配置与灰度发布四个运营件 [1]。这套骨架对个人中低频不是奢侈，是底线：砍掉 tick 级撮合、微秒延迟这些高频专属件是合理的，但 paper 环境、对账、独立 kill switch、PIT 数据四样"看似可选、实为必须" [1]。

选型走社区实证过的主流组合：**akshare 取数 → backtrader 仅作入门过渡件（Phase 2 学完即换）/ rqalpha 作 A 股回测长期内核 → miniQMT（或 easytrader）下单** [7][8]。决策权重记住一句话：**数据稳定性 > 回测正确性 > 下单可靠性 > 引擎先进性**（批次 B 实证结论）。全部使用免费开源软件，软件成本接近零；真正的成本是时间——按周末+晚上排期，从零到小额实盘大约需要 3~6 个月，急不得。

## 1. 动工前必须想清楚的三件事

### 1.1 策略频率定位：先承认自己是"中低频"，再决定砍什么

中低频（日线~小时级）最大的工程红利是**延迟预算从微秒级放宽到分钟级**：Python 批处理绰绰有余，FPGA、colocation、内核旁路、逐笔 tick 订阅、tick 级撮合仿真、微秒级延迟 SLO 全部可以省掉 [5][6]。这部分裁剪是安全的，砍掉它们不影响策略正确性，只影响"速度"。

但要分清"可以省"和"不能省"。有四样东西在高频语境下看似是性能件、在中低频语境下看似可省，实则全是安全件 [1]：

1. **Paper 模拟盘环境**——它是"接缝过滤器"。回测发现不了时区、序列化、网关异常码这类接缝问题，没有 paper 环境，这些问题全部集中在实盘第一周爆发。
2. **对账（reconciliation）**——断线期间丢失的成交回报不会自己回来，对账是发现"本地持仓与券商持仓发散"的唯一手段。
3. **独立于策略进程的 kill switch / 兜底平仓器**——策略失控时（订单风暴、fat-finger）的最后一根救命绳。挂在策略进程内的 kill switch 等于没有。
4. **PIT（Point-in-Time）数据层**——回答"当时只能看到什么"的问题，是防未来函数的第一道也是最后一道闸。

架构上还有一条长期主义原则：**回测与实盘共用同一套组件，只替换实现**。事件驱动架构（Event / Queue / DataHandler / Strategy / Portfolio / ExecutionHandler 五组件）使这种切换成为可能 [3]，vn.py 的 Gateway 抽象、rqalpha 的 Mod 化可替换设计都是这一思想的成熟实现 [2][4]。策略代码只写一次，环境差异收敛到适配器——这条原则越早定，后面越省钱。

### 1.2 投入预算与时间：零软件成本，但时间要诚实

预算有限是个好消息：本指南推荐的整条链路（Python + akshare + SQLite/Parquet + backtrader/rqalpha + vnpy/miniQMT + 自建脚本）全部开源免费。真正花钱的只有两处：一是行情/财务数据的商业授权（个人起步可先用社区源，但要知道它的合规与质量边界，见 §6）；二是部分券商的 QMT 权限门槛（有些券商要求一定资金量或交易量才开通，选券商时把这条问清楚，见 §2 Phase 5）。

时间的诚实比金钱的诚实更重要。三个典型错误预期：

- **"我周末写两天就能回测出能赚钱的策略"**——两天能搭出回测跑通，但回测结果不可信；可信需要数据层 PIT、成本模型、walk-forward，这些是数周的活。
- **"回测好 = 实盘好"**——回测和实盘之间隔着 paper 环境、对账、运维三座桥，跳过任何一座都是在真钱上调试生产路径 [1]。
- **"先跑起来，以后再补工程"**——补工程的最贵时刻是实盘事故之后。决策日志里 D-03 的教训可以迁移到这里：**把大任务拆成小步、每步落盘、控制最坏损失**（D-03 最终选择"拆两批小单并行 + 中间落盘"而非一次性大单，正是为了把失败损失从"全部"降到"≤2 个项目进度"）。

建议按"周末 + 工作日晚上"排期，给自己 3~6 个月到小额实盘的耐心。排期模板见 §5。

### 1.3 合规红线意识：程序化交易不是法外之地

个人量化最容易忽视、也最伤不起的是合规。两个必须知道的背景：

**监管趋势在收紧。** 程序化交易监管从规则制定走向落地执行，2024 年 2 月的灵均事件是标志性首案：2024-02-19 开盘 1 分钟内（媒体表述最短 42 秒），灵均投资通过程序化交易卖出沪深两市股票合计 **25.67 亿元**，随即在 2024-02-20 至 02-22 被沪深交易所采取**限制交易措施（3 个交易日）并启动公开谴责程序** [12][13][14][15]。这个案例说明：程序化下单的"速度优势"如果表现为对市场秩序的冲击（尤其开盘集合竞价后的脉冲式抛售），会直接招致交易所层面的处罚。个人资金量虽小，但"留痕报备义务真实存在"这一判断不受资金量影响 [1]——订单留痕、日志审计不是可选项，是监管语境下的基本动作。

**制度参数是活的，系统参数必须可配置。** 以涨跌停档位为例（截至 2026-08-27 核查口径 [9][10]）：

| 证券类型 | 涨跌幅限制 |
|---|---|
| 主板普通股 | ±10% |
| 主板 ST/*ST（2026-07-06 起） | ±10%（此前为 5%，已放宽统一） |
| 创业板 / 科创板（含风险警示） | ±20% |
| 北交所（含风险警示） | ±30% |
| 新股上市前 5 个交易日 | 无涨跌幅限制（既定规则） |

此外还有盘后固定价格交易扩展至全部 A 股及 ETF（15:05–15:30）、北交所拟新增风险警示股票单日累计买入（竞价+大宗+盘后）不超过 20 万股的限制（仅适用北交所风险警示股，实施时间以其另行通知为准，非全市场现行规则）[9]。这些数字直接决定回测撮合与风控参数——**把涨跌幅档位、交易时段、单票限额全部做成配置项而不是硬编码**，并在配置里记录生效日期，是本次 ST 新规（2026-07-06 生效）给我们上的最贵一课：5%→10% 的变化会让所有按旧档位建模的回测和风控集体失真。

合规底线清单（个人版）：① 订单与风控拒因全链路留痕，写只读存储；② 避免开盘/收盘集合竞价时段的高频脉冲式下单；③ 关注交易所程序化交易报备细则，拿不准就咨询券商或专业人士，不以"个人资金小"为由默认豁免；④ 不参与任何违法违规交易模式（如利用程序优势操纵价格、虚假申报等）。规则细节以交易所与证监会最新口径为准 [13]。

## 2. 分阶段路线图

总体原则：**每阶段都有明确产出物与验收标准，验收不过不进入下一阶段**。以下 7 个阶段对应架构基线的四环境演进 [1]。

### Phase 0：需求与环境（0.5~1 周）

- **目标**：搭好工作台，建立"一切可复现"的习惯。
- **产出物**：① 本地 Python 环境（建议 3.10+，`pyproject.toml` 或 `requirements.txt` + lock 文件锁版本）；② 一个 git 仓库（代码、配置、实验记录全部入库）；③ 实验记录模板（每次实验：日期、数据切片、参数、结果摘要、结论——手写 Markdown 即可，等实验多了再上 MLflow 类工具 [1]）；④ 一个 README 写清系统目标、频率定位（日线~小时级）、不做什么（不追 tick、不拼延迟）。
- **验收标准**：`git clone` 到新机器后能一条命令重建环境并跑通示例脚本；实验记录模板已落地并至少写了一条。
- **常见坑**：notebook 直连一切、环境不锁版本——akshare 这类高频发版的数据源库，不锁版本等于把"某天接口行为突变"埋进你的系统 [02b]；"先写代码后补文档"，结果三个月后没人记得第 47 次实验是什么（实验管理缺失的典型症状 [1]）。

### Phase 1：数据层（1~3 周）

- **目标**：建成可信的本地行情/财务数据库。**没有可信数据，回测结论本身不可信**——这是整个系统最重要的阶段，也是架构基线里"一切之前的数据与研究基础设施" [1]。
- **产出物**：
  1. **取数脚本**：akshare 为主（A 股覆盖全、免费、接口活跃，star ≈ 22.2k，截至 2026-08-27 检索值 [02b]），tushare（积分制，财务数据质量好）与 baostock（免费、稳定、接口变动少）作补充/双源校验。注意 akshare 痛点是源站变动导致接口偶发失效——**锁版本 + 结果缓存落地**是标准处方 [02b]。
  2. **复权处理**：日线用"不复权 + 复权因子表"或统一后复权口径，保证收益率序列跨除权除息日连续；**全系统只允许一种复权口径，并在表里标注**。除权日不做处理的后果是假跳空，动量/均线类信号全体失真 [1]。
  3. **PIT 意识落地**：每张表带 `asof` + `ingest_ts` 双时间戳，查询永远带 `ingest_ts <= :asof` 条件 [1]。个人起步可以简化：至少保证"财报数据带公告日字段、行情数据带时间戳"，并在因子计算时只用当时可得的数据。
  4. **落库与质量校验**：起步 SQLite 单文件足够（预算有限、单机、日线数据量小）；列式 Parquet 或 DuckDB 是下一步。写一个每日增量更新脚本 + 缺失/跳变体检（对应 Qlib 的 `check_data_health.py` [2]）：检查停牌日、异常涨跌、字段空值、复权因子跳变。
- **验收标准**：目标股票池（先小后大，比如沪深 300 成分 + 自选池）X 年日线齐全；复权因子表独立成表；质量体检脚本能输出"今日更新了 N 只、M 处异常"；增量更新能在 10 分钟内跑完（日线规模）。
- **常见坑**：① 只留现价在市的股票——**幸存者偏差**，退市股必须进历史库 [1]；② 除权日假跳空不处理；③ 财报数据用"最新披露值"回填历史——未来函数（PIT 的经典反面教材，财报重述是重灾区 [1]）；④ 爬虫源质量不设防——Qlib 官方都明示 Yahoo 数据"可能不完美"，社区源更要有体检环节 [1]。

### Phase 2：回测引擎（2~4 周）

- **目标**：让回测结果"可以相信"。回测引擎的选择本质是**向量式入门 vs 事件驱动长期主义**的取舍：
  - **向量式（pandas 逐行计算 / backtrader 类库）**：上手快、代码短，适合验证想法和教学；但天然有 lookahead 与成交模拟缺陷，撮合精度低 [3]。backtrader 本身已停更（第三方评测明确 "no longer actively maintained"）[02a]，**只建议用来入门，不建议作为长期依赖**。
  - **事件驱动（自研五组件 / rqalpha / vnpy 内核）**：回测与实盘共用组件、行为同构 [3][4]，是中低频系统的长期主义选择。rqalpha 原生内建 A 股规则（分红送转、涨跌停、T+1），Mod 化架构可替换数据源与扩展风控，个人自建系统可把它当"标准答案"对照 [02a]。
  - 务实路线：**用向量式/backtrader 快速验证想法，同时精读 rqalpha 源码或直接以它为回测内核**；实盘层用 vnpy [02a]。hikyuu（C++ 内核 + Python 层，原生适配 A 股，star ≈ 3.5k，截至 2026-08-27 检索值）可以作为"研究-回测一体化"的整体替代方案 [02b]。
- **产出物**：① 回测引擎（或 rqalpha 定制数据源）；② **成本与撮合模型**：手续费 + 滑点 + 印花税，参数可配置；③ **A 股约束建模**：涨跌停不成交（触及涨跌停的买单/卖单按规则拒绝或延迟）、T+1 持仓约束、最小报价单位、交易时段；④ **walk-forward 脚本**：滚动窗口训练-样本外测试，防过拟合；⑤ 回测单测（至少覆盖：除权日、涨跌停日、停牌日、T+1 卖不出）。
- **验收标准**：同一策略在引擎上跑出的结果可复现（固定随机种子 + 版本号）；把成本假设调高 50% 后收益排序不显著变化（稳健性冒烟测试）；涨跌停日成交模拟行为正确。
- **常见坑**：① **偷价**——用当日收盘价信号、当日开盘价成交，这是回测最常见的自欺；② 撮合模型过度简化，策略学会利用撮合漏洞"伪装成 alpha" [1]；③ 忽略涨跌停/T+1，回测里能成交的票实盘根本买不进；④ 全样本参数搜索后直接宣称策略有效——必须 walk-forward 或样本外验证 [1]；⑤ **涨跌停档位写死 5%**——2026-07-06 起主板 ST 已放宽至 10% [9][10]，参数必须配置化（见 §1.3）。

### Phase 3：绩效与风险评估（1 周，之后每次策略迭代都跑）

- **目标**：回答"这策略是真的好，还是幸存者运气"。接入评估框架文档的**六维自查**，每次策略评审按六维逐条过（具体条目以评估框架文档为准，本文给出与之一致的自查骨架）：
  1. **收益维度**：总收益、年化收益（必须扣费后口径）。
  2. **风险维度**：最大回撤、年化波动率、卡玛比率（年化/最大回撤）。
  3. **风险调整收益**：夏普比率——对"高夏普"保持警惕（Schwab 区间口径已经逐字核实：≥2.0 即可能暗示杠杆、需进一步调查，≥3.0 属 outstanding 稀有区间 [verify_facts 5a]）。
  4. **超额与稳定性**：相对基准的超额收益、月度正超额占比、IC/胜率，而非只看总曲线。
  5. **容量与约束**：换手率、单票集中度、触及涨跌停/停牌的比例——换手越高的策略对成本假设越敏感，容量越小。
  6. **鲁棒性**：walk-forward 样本外表现、参数敏感性（±10% 参数扰动后收益是否崩）、成本敏感性（成本翻倍后是否还能活）。
- **产出物**：策略评估报告模板（六维自查表 + 净值曲线 + 归因），每次迭代强制产出。
- **验收标准**：任何维度不达标都有明确处置结论（调参 / 放弃 / 降低预期资金）；报告归档进 git。
- **常见坑**：只看总收益不看回撤；把参数搜索后的最好结果当策略真实表现；忽视成本敏感性（实盘滑点往往比回测假设差 [1]）。

### Phase 4：模拟盘（4 周起，与实盘同等严肃）

- **目标**：把完整生产路径（取数 → 信号 → 组合 → 下单模拟 → 对账 → 报表）**影子运行 N 周（建议至少 4 周，覆盖跨月、除权除息、涨跌停等事件）**，让回测发现不了的接缝问题在真钱之前暴露 [1]。
- **产出物**：① paper 环境（走与实盘完全相同的代码路径，仅执行端换成影子撮合）；② **偏差报告**：模拟盘结果 vs 回测预期（收益、换手、滑点、成交率）的逐项对比；③ 接缝问题清单（时区、序列化、网关异常码、数据缺失处理）。
- **验收标准（准入门槛）**：影子运行满 N 周；偏差报告显示模拟与回测的关键指标偏差在预设阈值内（建议先定阈值再跑，避免事后找理由）；接缝问题清零或全部有修复记录；对账连续一致。
- **常见坑**：① paper 环境"随便跑跑"，没有准入门槛就进实盘——等于把生产路径调试放在真钱上做 [1]；② paper 与实盘代码路径不一致（比如 paper 手动下单），失去影子意义；③ N 周内没遇到任何事件（无除权、无涨跌停），强行放行——事件覆盖不足的模拟盘过滤不了撮合模型错误。

### Phase 5：小额实盘（第 1 周 = 最小可验证资金）

- **目标**：以最小资金验证真实链路，不追求收益，追求"链路正确 + 事故可控"。
- **券商通道选择**（场景表）：

| 通道 | 适用场景 | 优缺点（实证口径） | 成本门槛 |
|---|---|---|---|
| **miniQMT**（券商官方量化接口） | 首选：中低频自动化下单 | 官方接口稳定、支持 Python API、可编程撤单；easytrader 也已支持该通道 [02b] | 需券商开通权限，部分券商有资金/交易量门槛，开户前问清 |
| **QMT 客户端** | 全功能版 | 功能全但偏重、学习曲线陡；自带回测不建议用（社区实证倾向"放弃 QMT 自带回测，用 Backtrader+MiniQMT 组合" [7]） | 门槛通常高于 miniQMT |
| **easytrader** | 无权限时的替代 | 同花顺客户端模拟键鼠下单 + 雪球/掘金跟踪，A 股专属，star ≈ 9.2k（第三方盘点文快照，截至 2026-08-27 检索值）；**GUI 模拟路径脆弱易失效**，个人中低频优先走 miniqmt 官方接口路线 [02b] | 低，多数券商可用 |

- **灰度放量纪律**：首周用最低可成交资金（比如 1 万以内）跑 1~2 周；对账连续一致、偏差报告达标后再放大到目标资金的 1/10；每档放量后观察至少一周（覆盖交易周内的事件），全部平稳再进入下一档。**放量是单向门，只进不退的设计不是纪律，纪律是"每档都有明确的降级触发条件"。**
- **kill switch 与对账**：kill switch 必须是**独立于策略进程**的脚本/进程，一键平仓通道与策略本身解耦 [1]；对账做到"日内 + 日终"两两核对本地 vs 券商端（成交、持仓、资金）。
- **产出物**：① 实盘运行记录（含每笔订单、风控检查、拒因）；② 首周对账报告；③ 实盘 vs 模拟偏差报告。
- **验收标准**：首档资金运行 N 周无未解释的持仓差异；实盘成交率/滑点与模拟偏差在预设范围内；kill switch 演练过一次（真按，确认能平）。
- **常见坑**：① 断线期间丢回报不处理，带病开盘（对账是唯一发现手段 [1]）；② 把回测收益预期直接当实盘预期，第一周亏损就慌——实盘前三个月看的是"链路对没对"，不是"赚没赚"；③ 一上来就全仓自动交易，没有灰度。

### Phase 6：运营迭代（持续）

- **目标**：让系统"活着且被看见"，形成研究→实盘→研究的闭环。
- **产出物**：① **监控告警**：端到端各段延迟（数据更新延迟、信号生成延迟）、拒单率、状态机异常、对账差异设 SLO 并告警——"行情线程午休死掉、策略空转一周无人知晓"是最典型的事故形态 [1]；② **日志与审计**：订单全链路留痕（含每笔风控拒因），写只读存储，作为事故复盘唯一真相源 [1]；③ **报表回流**：每日 PnL 归因、实盘/模拟偏差、滑点对比，回流到研究侧——否则"实盘→研究"反馈断了，同一类滑点假设错误反复再犯 [1]；④ **策略退役流程**：定义明确的退役触发条件（如样本外回撤超阈值、偏差报告连续不达标、制度变更导致策略前提失效），触发后走"降级→停用→归档"流程，归档时保留完整版本快照以便复盘。
- **验收标准**：告警有人看（哪怕就是你自己，设好通知渠道）；每周有一次 5 分钟的对账与监控复盘；至少经历过一次完整的"告警→定位→修复→复盘"循环。
- **常见坑**：① 运维件堆在最后做——运营件从第一天就进版本库（§0 路线），Phase 0 就该有日志目录和留痕意识；② 事故复盘无真相源（没日志），靠回忆对线；③ 策略"永垂不朽"——没有退役流程的系统，最终被一个过时参数打爆。

## 3. 技术选型表

以下推荐全部锚定素材 02a/02b 的实证结论；star 数均为**截至 2026-08-27 检索值**（部分为间接来源，见注）。

| 类别 | 推荐组合 | 替代项 | 选择理由（实证口径） |
|---|---|---|---|
| 语言生态 | Python 3.10+（pandas/numpy 生态） | 局部可选 Rust/C++ 内核（hikyuu 内建） | 中低频分钟级延迟预算下 Python 批处理绰绰有余 [1]；nautilus_trader（Rust 核 + Python 接口，生产级事件驱动）工程范式是天花板级参考，但对个人中低频**过重**，只借鉴思想 [02b] |
| 存储 | SQLite 起步 → Parquet/DuckDB 列式进阶 | HDF5/bin（Qlib 风格紧凑列式 [1][2]） | 日线级数据量 SQLite 足够；列式存储解决迭代速度问题 [1]；预算有限不引入时序数据库 |
| 回测框架 | 入门 backtrader（学习）→ 内核 rqalpha（A 股原生、Mod 化）或自研事件驱动 | hikyuu 整体替代（C++ 内核、原生 A 股）；vnpy 事件驱动引擎；qlib 借鉴因子与研究管线思想 | rqalpha 原生内建 A 股规则（分红送转/涨跌停/T+1），持续迭代（changelog 至 2026-07-27）[02a]；backtrader 已停更，只借鉴 Strategy/Indicator/Broker 解耦思想 [02a]；qlib 平台级重依赖对个人集成成本高，只借鉴 AI 因子挖掘与研究管线设计（star ≈ 33.7k）[02a] |
| 数据源 | **akshare 主**（免费、A 股覆盖全、star ≈ 22.2k），tushare/baostock 双源校验 | 商业数据（预算充足时考虑）；Qlib 内置 A 股工具可参考 | akshare 原生覆盖 A 股、接口活跃、版本高频滚动 [02b]；痛点是源站变动接口偶发失效 → 锁版本+缓存落地 [02b]；社区实证有从 tushare 迁移 akshare 的实践 [8] |
| 下单通道 | **miniQMT 官方接口首选**；easytrader 兜底 | QMT 客户端；vnpy 券商 gateway 层 | 实证主流组合 = akshare/backtrader/miniQMT 或 easytrader [7][8]；easytrader 支持同花顺客户端 + miniqmt 双通道（star ≈ 9.2k），GUI 模拟脆弱、优先官方接口 [02b]；vnpy 提供 A 股 gateway 与实盘工程经验（star ≈ 29.7k）[02a] |

选型总原则：**不为先进买单，只为正确买单**。nautilus_trader 的架构、qlib 的 AI 流水线都值得精读借鉴，但个人中低频系统的正确姿势是"吸收思想、自建轻量实现"，而不是扛起平台级依赖 [02a][02b]。

## 4. 常见坑点清单（症状 → 处方）

1. **未来函数**：症状——回测收益高得离谱，换数据切片结果大变（财报重述后旧信号消失）；处方——所有表带 `asof`/`ingest_ts`，查询强制 `ingest_ts <= :asof` [1]。
2. **偷价**：症状——信号与成交同用当日收盘价，策略"恰好"买在最低卖在最高；处方——信号用 T 日收盘，成交按 T+1 开盘（或至少按下一 bar 开盘）模拟。
3. **复权口径混乱**：症状——除权日出现假跳空，均线/动量信号在除权日集体失真；处方——全系统统一一种复权口径并落表标注 [1]。
4. **幸存者偏差**：症状——历史收益好，但股票池里没有退市股；处方——退市股必须进历史库，股票池按"当时存在"选取 [1]。
5. **过拟合**：症状——参数搜索出来的"最优参数"样本外失效；处方——walk-forward 滚动窗口测试 + 参数敏感性分析 [1]。
6. **撮合漏洞被策略利用**：症状——策略专挑"回测能成交"的场景下单；处方——保守撮合模型 + 涨跌停/T+1/最小报价单位约束建模 [1]。
7. **成本假设乐观**：症状——高换手策略回测年化 30%，实盘 5%；处方——手续费+滑点+印花税全算上，成本翻倍做压力测试 [1]。
8. **涨跌停档位写死**：症状——2026-07-06 后主板 ST 已 5%→10%，旧系统还在按 5% 撮合 [9][10]；处方——制度参数配置化并带生效日期。
9. **T+1 约束缺失**：症状——回测当日买当日卖；处方——持仓表中强制 T+1 可卖约束。
10. **部署事故**：症状——Knight Capital 式：代码改了一半、8 台服务器只部署了部分、97 封自动化报错邮件没人看，45 分钟发出超 400 万笔订单（本意只成交 212 笔客户订单）、成交超 3.97 亿股、损失超 4.6 亿美元（SEC 终局口径），并为此支付 1200 万美元和解 [11]；处方——灰度部署、全量一致性校验、告警必看。
11. **断线丢回报不处理**：症状——本地持仓与券商持仓悄悄发散，第二天带病开盘；处方——日内+日终两两对账 [1]。
12. **kill switch 挂在策略进程里**：症状——策略死循环时 kill switch 也死了；处方——独立进程/脚本的兜底平仓通道 [1]。
13. **notebook 直连实盘式开发**：症状——"第二个策略出现时"系统崩溃（quant67 对 notebook+cron 结构的判决 [1]）；处方——环境隔离：研究环境不碰实盘凭据。
14. **数据源接口突变**：症状——akshare 某天接口报错，行情断更一周没人发现；处方——锁版本 + 缓存落地 + 数据新鲜度告警 [02b]。
15. **实验不记录**：症状——"第 200 次实验后没人记得第 47 次是什么" [1]；处方——实验模板 + git 归档，参数和数据切片可复现。
16. **配置四环境漂移**：症状——回测、paper、live 参数不一致，偏差报告失真；处方——配置版本化（strategy.yaml 入库），环境差异收敛到适配器 [1]。
17. **策略永垂不朽**：症状——策略失效很久还在跑，净值被慢慢磨掉；处方——退役触发条件写进策略文档，触发即走降级→停用→归档。
18. **把回测收益当实盘预期**：症状——实盘第一周亏损就心态崩坏、手动干预；处方——实盘初期看"链路正确性"，收益预期只信偏差报告 [1]。

## 5. 优先级排序与最小可行路径（只有周末时间怎么排期）

**优先级总排序**：可信数据 > 保守回测 > 绩效评估 > 模拟盘 > 小额实盘 > 优化迭代。任何"优化"（更快的引擎、更炫的因子）都排在"正确"后面。

**周末版排期模板**（3~6 个月）：

| 时间 | 内容 | 里程碑 |
|---|---|---|
| 第 1 个周末 | Phase 0 + Phase 1 起步：环境、git、实验模板；akshare 日线落 SQLite | 数据入库，质量体检脚本跑通 |
| 第 2~3 个周末 | Phase 1 完成 + Phase 2 起步：复权表、PIT 字段；backtrader 跑通第一个示例策略 | 复权正确、回测可复现 |
| 第 4~5 个周末 | Phase 2 完成：成本模型 + A 股约束（涨跌停/T+1）+ walk-forward | 约束建模验收通过 |
| 第 6 个周末 | Phase 3：六维自查 + 策略评估报告 | 第一份策略报告归档 |
| 第 7~10 个周末 | Phase 4：paper 影子运行（工作日晚上看告警/对账即可） | 4 周偏差报告达标 |
| 第 11~12 个周末 | Phase 5：开通 miniQMT 权限、首档小额实盘 + kill switch 演练 | 首档资金运行平稳 |
| 之后 | Phase 6 持续 + 灰度放量 | 按偏差报告逐档放大 |

**最小可行路径（实在挤不出时间的缩水版）**：akshare + SQLite → 一个简单策略（如均线类）backtrader 回测（含成本与 T+1 约束）→ paper 手工模拟 2 周（脚本出信号、手工记录）→ miniQMT 最小资金自动化。缩水版可以砍掉"多策略并行、因子挖掘、自研引擎"，**但砍不掉对账、留痕、kill switch 三样**——它们是安全件不是优化件 [1]。

## 6. 风险与局限声明

1. **不构成投资建议，不承诺收益。** 本文所有技术路径只解决"系统如何构建"，不解决"什么策略赚钱"。历史上头部量化机构也会遭遇超额收益大幅回撤：幻方量化 2021 年 9-12 月量化超额回撤后，于 2021-11-15 宣布暂停旗下全部产品申购（含追加），2021 年 12 月底公开道歉并免除多只产品赎回费 [16][17][18][19]——专业机构的策略都会阶段性失效，个人更要管理预期。
2. **制度数据有时效性。** 本文涨跌停档位、交易时段等数字为 2026-08-27 核查口径（2026-07-06 起生效的 ST 新规等）[9][10]；监管细则（程序化交易报备、风险警示股票买入上限等）持续演进，落地时间与执行细节以交易所/证监会最新口径为准 [13]。
3. **数据源合规与质量风险。** akshare 等社区源是爬虫/聚合产出，接口可能随源站变动失效 [02b]，数据质量需自设体检环节；商用数据（如 tushare 积分、rqdatac）质量与合规更优但需付费 [02a]。商业用途请自行核实数据授权。
4. **技术方案是个人级，非机构级。** 不涉及微秒级组件、商业机房、多租户架构；本文一切"必须件"指的是防自毁的安全件（对账、PIT、kill switch），而非机构级高可用。
5. **个人精力的局限。** 单人运维意味着告警即是你、对账即是你——任何"没人看"的自动化都是假自动化。若连续多周无法保证每周复盘，应主动缩小资金规模而非扩大。
6. **高夏普警惕。** "夏普 ≥3.0 属 outstanding、多数落 1.00–1.99"为 Schwab 官方区间且经逐字核实 [verify_facts 5a]；其另提示 ≥2.0 即需调查。"异常高夏普通常意味着回测漏洞或过拟合"属从业者经验法则 [J]（DSR 多重检验提供机制支撑），回测自查时把"高夏普"当作红旗而非勋章。
